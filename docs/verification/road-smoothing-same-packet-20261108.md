# 同地图包多色道路平滑对照（2026-11-08）

## 结论

现有四邻 RGB565 颜色平滑适配语义多色地图后，可以柔化旋转时的像素阶梯，但无法消除源材质网格已经存在的道路、建筑毛边。ESP32-S3 实际双核绘制计时中，两组真实地图的中位耗时均约由 34 ms 增至 78 ms；72/72 组未通过不超过 10% 增幅的目标。不建议直接启用此候选。

正式固件源码没有改动。只在独立副本中启用采样器，测试后恢复圆屏原应用分区，回读 3 MiB 与备份逐字节一致，正常启动。

## 输入与对照方法

- 明波立交真实 v2 道路包：`output/map-edge-bridge/road-palette-qa/06-mingbo/roads.bin`。
- 人民广场固定高度 1 米的真实 v2 建筑包：`output/amap-flat-source-20261108/capture-height/04-height-1m/production-building.bin`。
- 每个对照使用同一地图包、坐标、主题调色板、昼夜、旋转及缩放；不增加地图分辨率，不新增材质或线格式。
- 基线为最近邻采样。候选为生产 `RasterSmoothing.h` 中的四邻颜色混合，纯色块保持快速路径；只放开语义调色板限制并建立纯色／混合索引。缺少有效邻点保留原采样。本轮没有测试跨新旧包补边。
- 实际源码还将 `MOTONAV_RASTER_SMOOTHING` 默认设为 0，且解码、工作队列和渲染入口排除调色板包。此前只有“平滑存在”不能说明当前正式多色地图正在使用它。

## 静态与宿主验证

- 使用 `systematic-debugging`、`esp32-test-plan`，按静态、宿主、设备绘制及恢复分层。
- ESP32 workbench project doctor：0 错误，已有 BOOT GPIO0 启动绑带警告；Arduino 工程没有 sdkconfig，工具未分析到任务栈，因此不是完整运行时安全证明。
- 既有 raster-smoothing 宿主回归通过：RGB565、块边界、坐标接缝、三主题昼夜、原子换图、取消及分配失败回退。
- 新宿主程序提取生产 `rasterRows`；基线移除编译关闭的平滑部分，候选适配语义调色板。使用实际 466×466、CX=233、MAP_PY=262 和原圆形边界规则。
- 两个样本 × 三主题 × 昼夜 × 0°/45°/90° × 0.6/0.38 缩放，共 72 个配置。每配置交替测量 31 次／模式，分别取中位数；包和源文件 SHA 见 `source-manifest.json`。
- 宿主预览只显示地图，没有导航 HUD；CPU 时间不替代设备结果。最近邻放大用于看清差异，不用额外图片平滑美化候选。

## ESP32-S3 实测

采用当前工程及已安装的 ESP32 Arduino core 3.3.10 构建临时诊断。复用真实 `drawRasterMap`、`parallelRows`、双核行绘制、PSRAM 地图缓冲与实际 framebuffer。冻结地图，不在计时循环内输出日志或截屏。每个计时帧后让出 CPU，防止长时间基准测试饿死空闲任务。

基线与候选在同一诊断固件中切换，基线也包含候选开关检查。这是地图绘制耗时，不是整个 App 导航帧率，也不是对两个正式固件的整机 FPS 比较。

| 样本 | 配置数 | 基线中位数 | 平滑中位数 | 配对增幅中位数 | ≤10% |
| --- | ---: | ---: | ---: | ---: | ---: |
| 明波道路 | 36 | 33.925 ms | 77.701 ms | +128.9% | 0/36 |
| 人民广场建筑／道路 | 36 | 33.838 ms | 77.789 ms | +130.7% | 0/36 |

- 所有配置均有非零 framebuffer 像素差异，说明候选路径实际执行，不是基线对基线计时。
- 原地图 RLE 字节不变，不增加协议或地图传输字节。
- 每个当前块索引表 5,625 B。正式双缓冲接入通常还需备用块索引；本轮未证明完整接入峰值内存门槛。
- 分步扫描含主动让出时间约 324.6 ms／263.4 ms，不将其当作纯 CPU 时间，也没有把它计入稳定帧绘制计时。
- 诊断临时增加一份完整 framebuffer 用于比较，测后释放；它不是候选发布所需常驻内存。
- 串口没有发现 Guru Meditation、Stack canary、任务看门狗触发或诊断失败标记。

## 未测与下一步边界

本轮未测手机 CPU／峰值内存、实际 BLE 吞吐／ACK、换图低帧率窗口、导航并发与 G 采样，也没有完成用户实屏目检。源地图覆盖和几何正确性保持原输入的局限。

这次对照否定的是“直接启用现有四邻颜色平滑即可低成本解决毛刺”，不代表所有边界处理方案都不可行。下一轮应先区分源网格毛边与旋转采样阶梯，使用同源局部预览验证边界处理是否真正改变形状；不要继续靠全图加分辨率或全图逐像素混合来掩盖问题。
